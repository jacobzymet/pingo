# Pingo v1 wire protocol

The protocol uses standard cryptographic primitives. The PSK must be
32 randomly generated bytes. Both roles authenticate using that same key;
use a unique key for every peer pair. There is no forward secrecy.

All integer wire fields use unsigned network byte order. Outer traffic consists
of IPv4 ICMP echo requests, type 8/code 0, identifier `0x5047`, a sequence number,
and the standard ICMP checksum. Sequence numbers and the identifier are carrier
fields, not authentication. Only the configured outer source IPv4 address is
accepted. Echo replies and malformed/fragmented outer packets are ignored.
The raw carrier does not suppress OS echo behavior. Optional VPN kill-switch
policy is separate from this wire framing.

ICMP itself supplies no reliable delivery, packet ordering, or connections.
Pingo implements session/connection management in `transport.Endpoint`, and
direct-transfer ordering/reassembly and retransmission in `reliable.Reliable`.
VPN mode shares the session protection but carries best-effort datagrams.

## Session establishment

Mode is one byte: ASCII `D` for direct transfers or `C` for congestion-aware VPN.
Legacy VPN mode `V` is not accepted by version 0.2 peers. HMAC here means
HMAC-SHA256 using the PSK over `b"pingo/handshake/v1\x00" + body`.

1. Initiator generates a fresh 32-byte challenge `C` and sends
   `b"PGH1" + mode + C + HMAC(body)` (69 bytes).
2. Responder authenticates the request, generates a fresh 32-byte challenge `S`,
   and replies `b"PGH2" + mode + C + S + HMAC(body)` (101 bytes).
3. Each role uses HKDF-SHA256: input key material = PSK, salt = `C + S`,
   info = `b"pingo/session/v1"`, length = 64 bytes. The first 32 bytes encrypt
   initiator-to-responder; the last 32 encrypt responder-to-initiator. The session
   ID is the first 16 bytes of SHA-256 of `b"pingo/id/v1" + C + S`.
4. Initiator authenticates the response and checks its own current challenge and
   mode. It sends encrypted `b"\x10" + mode` (FINISH).
5. Responder adopts the pending session only after authenticating FINISH, resets
   application state, then sends encrypted `b"\x11" + mode` (READY).
   Initiator considers the connection usable only after authenticating READY.

Both challenges are fresh after every process restart. Sessions/counters are
never persisted or restored. A replayed signed HELLO elicits a new responder
challenge, so an old FINISH/data packet cannot establish the old session. Repeated
identical HELLO within a pending handshake reuses its response to tolerate loss.
There is one pending candidate, expiring in 45 seconds; new candidates are rate
limited to one per 250 milliseconds. FINISH retries use fresh encryption counters
and elicit a new encrypted READY. Confirmed reconnection supersedes the old
session; concurrent initiating processes are unsupported. Replaying signed
HELLOs can still disrupt the handshake, which is an acknowledged DoS limit.

## Protected packet

| Field | Bytes |
| --- | --- |
| Magic/version `PG01` | 4 |
| Session ID | 16 |
| Packet counter | 8 |
| ChaCha20-Poly1305 ciphertext and full tag | variable, including 16-byte tag |

The entire 28-byte header is associated data. Nonce is four zero bytes followed
by the eight-byte packet counter. Counters start at zero independently in each
direction under different keys, increase for every encryption including retries,
and stop before 2^32. Encrypting is serialized. Never reuse a Session object to
restart a connection. The ICMP payload limit is 1,200 bytes; plaintext is 1–1,156.

The receive window retains the highest authenticated counter and a 1,024-bit
bitmap. Counters older than that window or already seen are rejected. Neither
window nor liveness timestamp changes for invalid tags or replayed packets.
Only the reader thread decrypts or changes incoming session state.
This window provides replay protection, not packet resequencing or loss recovery.

Protected control values are FINISH, READY, one-byte PING (`0x12`), and PONG
(`0x13`). Each established endpoint sends a PING every five seconds. Authenticated
inbound traffic maintains liveness. At 30 seconds without inbound traffic,
initiators and VPN responders terminate; direct-mode responders discard the
session and incomplete transfers and continue listening for a fresh handshake.
Reconnection requires a fresh endpoint/handshake. CLI supervisors perform bounded
automatic recovery with fresh challenges. Persistent VPN responders discard
inactive sessions and wait for another authenticated initiator while retaining TUN.

## Reliable direct blobs

Protected plaintext is: kind (1 byte), operation ID (16), fragment index (2),
fragment count (2), body. Kind is DATA `0x01` or ACK `0x02`.
DATA bodies are 1–1,000 bytes; all nonfinal fragments are exactly 1,000 bytes.
Blobs are at most 65,536 bytes / 66 fragments. Each sender serializes its blobs
and increments a per-session operation counter, encoded as a 16-byte integer.

The sender waits for each fragment's ACK before sending the next fragment.
The receiver reassembles only the next sequential fragment for an operation;
future fragments are ignored rather than buffered out of order.
Accepted duplicate fragments get another ACK. Final ACK body is a status byte
(`0` success, `1` error) plus at most 255 bytes of application result/error.
The application runs before the final acknowledgment. Sender retries a fragment
with a new AEAD counter and bounded timeout/attempt count after missing DATA or
ACK delivery. First-attempt acknowledgments feed an RTT/variance estimator;
retransmitted samples are excluded. Loss doubles the timeout, bounded to two
seconds, with the configured initial timeout as its floor. Exhausting retries
reports a timeout, not guaranteed delivery. Direct transfers are not pipelined.

At most four incomplete blobs exist and expire after 45 seconds without progress.
At most 128 completion results remain, for at most 60 seconds. A completion
watermark retires older operation IDs even after result eviction; retired requests
without a result are ignored, never executed again. Applications must treat
timeout as an ambiguous result: the recipient may have completed the operation.
A brand-new command/session is a new operation and may repeat user intent.

Application blob first byte selects:

| Operation | Body |
| --- | --- |
| MESSAGE `0x20` | UTF-8 text, at most 60,000 bytes |
| BEGIN `0x21` | JSON (`id` 16 bytes as hex, `name` string, `size` integer), at most 512 bytes |
| CHUNK `0x22` | Transfer ID (16), offset (8), file bytes (1–32,768) |
| END `0x23` | Transfer ID (16), SHA-256 digest (32) |
| ABORT `0x24` | Transfer ID (16) |

One file is open at a time. Chunks must match the current ID and exact next
offset without exceeding declared size. Completion requires exact size and hash,
file fsync, atomic publication without overwrite, and directory fsync on POSIX.
Windows uses same-directory no-overwrite rename; POSIX uses exclusive hard-link
publication then removes the temporary name. The receiver controls its directory
and sanitizes/ prefixes the name. Private local filesystem directories are
required; unsupported atomic filesystem operations produce visible errors.
Legacy partials expire after 60 seconds; exit/session reset removes them.

### Resumable file extension

RESUME `0x25` carries JSON with exactly `id` (16 bytes as lowercase hex), `name`
(at most 60 characters), `size` (integer), and `digest` (SHA-256 as lowercase hex),
at most 768 bytes. The sender derives identity as the first 16 bytes of SHA-256
of `b"pingo/file/v2\x00" + digest_bytes + name_utf8`. Existing direct operations
keep their formats.

The response is JSON: `{"complete":false,"offset":N,"prefix":SHA256_HEX}` or
`{"complete":true,"name":RECEIVER_FILENAME}`, within the reliable result bound.
The sender verifies prefix/offset before reusing data. CHUNK/END retain existing
formats; END must also match the initially declared digest.

Each resumable CHUNK is fsynced before an atomic, fsynced JSON checkpoint advances
the acknowledged offset. A restarted receiver truncates uncheckpointed trailing
bytes and rebuilds the prefix hash. Completion uses atomic no-overwrite publication;
a final file is reverified if a crash interrupted the completion record. Lost final
acknowledgments do not publish another copy. The sender validates the receiver name.

Session reset/shutdown closes resumable streams without deleting checkpoints.
At most 128 records persist, default 24 hours. Remaining incomplete bytes reserve
receive quota. Expiry removes records/partials, retaining final files. Record paths
are derived only from validated hexadecimal IDs in a private receiver directory.
No keys, nonce counters or transport-session state are persisted. Recovery starts
with RESUME in a fresh session; ambiguous messages are not replayed automatically.

## VPN datagrams

Protected plaintext is `0x03` followed by exactly one IPv4 datagram, at most
1,000 bytes, without a TUN packet-info header (`IFF_NO_PI`). Validate version,
header length/checksum, declared total length, and inbound source allowlist
before writing to TUN. Inner IPv4 fragments are permitted; IPv6 is rejected.
There is no VPN retransmission, reassembly, compression, or packet batching.
Legacy `0x03` datagrams are accepted within the new VPN mode. New outbound data
is `0x05` + 64-bit sequence + IPv4 packet. Acceptance produces authenticated
feedback `0x04` + sequence. Invalid packets get no acknowledgment. Feedback is
best-effort and does not trigger datagram retransmission.

The sender starts with a four-packet window, adds `1/window` per acknowledgment,
and caps the window at 64. Expired datagrams halve the window at most once per
loss-timeout interval. Outstanding state is bounded by the window. Smoothed RTT
sets pacing/loss timeout, with a 200-data-packet/sec cap. New sessions reset this
state. Kernel congestion drops packets.
Routes and TUN are Linux application concerns, independent of session encryption.

Valid VPN datagrams are written to TUN in arrival order within the replay window;
Pingo does not restore their original order or recover missing packets. Inner
TCP supplies its own reliability and congestion control; UDP applications must
handle loss/ordering when needed. The adaptive window and packet-rate cap are
congestion responses, not a complete TCP-compatible congestion-control algorithm.
